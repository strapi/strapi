# Spike CMS-1943: data lifecycle (seed, snapshot, restore)

RFC decisions D3 and D4. Branch `spike/cms-1943-data-lifecycle`, on top of the `/tests-next` scaffold (#28427). Not meant to be merged: the code here is a proof of concept for CMS-1945, CMS-1947 and CMS-1950.

## Setup

- App: the e2e test app (`test-apps/e2e/test-app-0`, generated by `yarn test:e2e --setup`), SQLite, admin built once, served with `strapi develop --no-watch-admin --no-build-admin` (D8).
- Machine: local macOS. Not run in CI or under Playwright.
- Code:
  - `tests-next/shared/test-plugin/`: a test-only plugin, enabled with `STRAPI_TEST_PLUGIN=true` and loopback requests only. Endpoints: `GET /api/tests/boot`, `POST /api/tests/snapshot`, `POST /api/tests/reset` (D1), `POST /api/tests/restore-sql` (D2), `POST /api/tests/export-dts` and `POST /api/tests/restore-dts` (option 3).
  - `spike/seed.js`: in-process seed.
  - `spike/measure.js`: full lifecycle and D1 timings.
  - `spike/compare.js`: D1, D2 and option 3 against the same consistency checks.
  - `spike/baseline.js`: today's reset (`POST /api/config/reset-fixture`, #28302).

## Results

| Step                                                                                       | Time                                                          |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| A. Content type written to `src/api` before boot                                           | Synced on the first boot, no restart                          |
| B. In-process seed: `createStrapi().load()`, 3 admin users, 2 entries, `destroy()`         | 3.3 s (2.4 s of it is `load()`)                               |
| C. Cold boot to first response                                                             | 2.7 s                                                         |
| D. Admin login through the API                                                             | 75 ms                                                         |
| D. Online snapshot (`VACUUM INTO`)                                                         | 14 to 18 ms, 2.3 MB                                           |
| **D1. Restore the snapshot file in `register()` during a worker reload**                   | **median 1.7 s** (1.65 to 2.1 s, 10 runs)                     |
| **D2. Copy every table back from the snapshot (`ATTACH` + `DELETE`/`INSERT`), no restart** | **median 17 ms** (50 runs)                                    |
| Option 3. Export the seeded state as DTS, restore it in process                            | median 287 ms, rejected (see below)                           |
| Today: `reset-fixture` (fixed `with-admin` export, #28302)                                 | median 101 ms, 163 ms with the login every test does after it |

### Consistency checks

Every round writes state Strapi may hold in memory, resets, then checks it through the HTTP API only:

- a new admin role, and the Editor role stripped of all its permissions (the editor's own request to the Content Manager goes from 200 to 403, so the permission engine is involved);
- a new locale set as the default (i18n keeps the default locale in the core store);
- a new admin user and a new entry.

| Method       | All checks pass                                                           | Tokens still valid after the reset |
| ------------ | ------------------------------------------------------------------------- | ---------------------------------- |
| D1 reload    | yes                                                                       | yes                                |
| D2 SQL copy  | yes, 50 times in a row                                                    | yes                                |
| Option 3 DTS | no: admin roles and users are duplicated, and ids change on every restore | no: everyone is logged out         |

## Findings

1. **Schemas before boot work.** Writing `schema.json` files before the first boot is enough: bootstrap syncs them. Scaffolders don't need a running server or a restart.
2. **The DB connection opens in bootstrap, after the plugins' `register()`** (`packages/core/core/src/Strapi.ts`, `bootstrap()` → `db.init`). A test plugin can therefore swap the DB file in `register()` safely. This is what makes D1 work.
3. **Admin tokens depend on a DB row.** `strategies/admin.ts` calls `isSessionActive(sessionId)`, so a token is only valid while its session row exists. Take the snapshot **after** the logins of each role (D5): D1 and D2 then keep every `storageState` valid across resets. Anything that rewrites the sessions or the admin users (option 3) logs everyone out.
4. **D2 is fast and, for what we checked, consistent.** The permission engine and the i18n default locale read the DB again after the copy. It is 100 times faster than D1, and faster than today's `reset-fixture`, while starting from a seeded state we can regenerate (the D3 goal) instead of a fixed export.
5. **Option 3 is not worth it.** The DTS `restore` strategy does not delete admin entities before inserting them (protected types), it remaps ids, and it is 15 times slower than D2. #28302 works around this with custom code for admin entities.
6. **Today's baseline changed after the RFC.** #28302 (Nov 3) restores the fixed export in process in about 100 ms. Snapshot by restart (D1) would be slower than today; D2 is not.

## Recommendation

- **Default reset: D2** (in-process SQL copy from a snapshot), for both `resetScope: 'file'` and `'test'`.
- **Fallback: D1** (reload) when the schema changed since the snapshot, i.e. content-type-builder tests. D2 assumes the live DB and the snapshot have the same tables and columns; a reload resyncs the schema.
- **Snapshot once per run and per edition**, after the seed and the role logins, with `VACUUM INTO` from the running server.
- The RFC fallback (per-file seeding without a snapshot) is not needed.

## Notes for the implementation tickets

- **CMS-1945 (app lifecycle):** generate, build the admin once, run the seed in process before the first boot (3.3 s), then boot once (2.7 s). The test plugin is loaded through `config/plugins.js` with `resolve`, enabled by `STRAPI_TEST_PLUGIN=true`.
- **CMS-1947 (scaffolders and seeders):** scaffolders write schema files before boot. Seeders run in process with `createStrapi().load()` and the services or the Document Service. Admin users are created with `strapi.service('admin::user').create` and the default role codes (`strapi-super-admin`, `strapi-editor`, `strapi-author`). The seed is quick (about 200 ms for users and entries); `load()` dominates.
- **CMS-1950 (DB reset scopes):** `snapshot` = `VACUUM INTO`, `reset` = D2, `resetAfterSchemaChange` = D1. Expose them from the test plugin. Wait for `GET /api/tests/boot` to return a new pid after D1.
- **CMS-1948 (test plugin):** this spike is a first version of it: loopback-only, env-gated, no auth.

## Limits

- SQLite only. The E2E suite only runs on SQLite; API tests (Postgres, MySQL) need another approach (one instance per file, D4).
- `restore-sql` turns `foreign_keys` off and runs `ATTACH` on the live connection. It relies on the SQLite pool having a single connection (the knex default).
- Requests in flight during a reset are not handled. Resets happen between tests, when the browser is idle.
- Caches not checked: Content Manager view configurations, upload and users-permissions settings, and anything a plugin caches in its own memory. To add to the checks in CMS-1950.
- Small dataset (3 users, 2 entries, a 2.3 MB DB). D2's cost grows with the DB size; D1's mostly doesn't.
- Local macOS timings, not CI.
